## 1. End-to-End Pipeline Trace & Architecture

The ingestion pipeline links raw bank scrapers to controlled consumer publication through an unbroken, evidence-grounded execution trace:

```text
Bank Web/API Source
        ↓
Bank-Specific Scraper (`src/banks/<bank>/`)
        ↓
Bank-Specific Parser & Normalizer (`src/parsing/`)
        ↓
Normalized Offer Candidate (`Offer` domain object)
        ↓
Evidence Indexer (`src/parsing/validators/offer-evidence.ts`)
        ↓
Deterministic Rule Validation (`OfferValidator` - ISO dates, expiration, ranges)
        ↓
Selective Multi-Turn LLM Validation (`runLlmToolCallingSession` - DeepSeek / Gemini)
        ↓
Allowlisted Tool Execution (`OfferToolExecutor` - 22 sandboxed inspection tools)
        ↓
Zod Schema Validation (`FullOfferValidationProposalSchema`)
        ↓
Field-Specific Evidence Verification (`OfferCorrectionValidator` - Invariant guards)
        ↓
Geolocation Validation (`ValidationOrchestrator` - Scope, branch matching, zero-spoof)
        ↓
Duplicate & Candidate Update Detection (`detectAndRecordDuplicates`)
        ↓
Quality Decision Gate (`VALIDATED` | `REVIEW_REQUIRED` | `INVALID`)
        ↓
Database Staging (`upsertOffer` with Fencing Token into PostgreSQL)
        ↓
Operator Review Console (Cloudscape Admin Dashboard `OfferReviewWorkspacePage`)
        ↓
Controlled Publication (`syncApprovedOffer` / `transitionOffer` -> `PUBLISHED`)
```

## 2. Production Entry-Point Integration

### 2.1 Unified Validator Wiring in Scraper CLI (`src/cli/scrape.ts`)
The production CLI entry point (`src/cli/scrape.ts`) executes the actual `ValidationPipeline`:
1. **Evidence Grounding & Batch Validation**:
   ```typescript
   const pipeline = new ValidationPipeline({
     llmValidator,
     forceLlm: llmEnabled,
     sampleRate: llmEnabled ? 100 : 0,
     minimumLlmScore: 70,
     getReusableLlmValidation,
   });
   const reports = await pipeline.validateBatch(offers);
   ```
2. **Effective Offer Staging**:
   When accepted corrections are generated by the unified pipeline, the scraper persists `report.unifiedValidation.effectiveOffer`:
   ```typescript
   const stagedOffer = report?.unifiedValidation?.effectiveOffer ?? offer;
   const result = await upsertOffer(stagedOffer, runId, { lifecycleStatus }, fencingToken);
   ```
3. **Fail-Open Detection**:
   Offers where LLM calls fail after retries are flagged with `LLM_VALIDATION_FAILED` and routed to `REVIEW_REQUIRED` rather than masquerading as clean passes.

## 3. Database Lifecycle & Isolation Invariants

Executed against disposable, WASM-isolated PostgreSQL (`RealPostgresHarness` / PGlite):

| Test Condition | Expected Behavior | Observed Result | Status |
|---|---|---|---|
| **Public Query Isolation** | `SELECT * FROM offers WHERE db_status = 'PUBLISHED'` returns 0 unapproved/unsynced offers | Exactly 0 records returned | **PASS** |
| **Controlled Publication** | `syncApprovedOffer(id)` validates and publishes only `APPROVED` offers | Exactly 1 offer transitioned to `PUBLISHED` | **PASS** |
| **Immutable Live Offers** | Re-scraping modified bank offer updates `pending_candidate`; live `PUBLISHED` offer stays intact | Live discount remains 20%; candidate discount 35% staged in `pending_candidate` | **PASS** |
| **Sacred Manual Overrides** | Re-scraping offer with existing `manual_override` preserves admin corrections | Admin curated merchant name remains intact after re-scrape | **PASS** |
| **Distributed Fencing** | Worker with stale lease generation is rejected by database constraint | Throws `Fencing violation: expected gen 1, lease has gen 5` | **PASS** |
| **Deterministic Publish Guard** | Expired or invalid offers cannot be published even via explicit sync | Sync returns `{ outcome: 'failed', reason: 'final validation failed' }` | **PASS** |
| **Upstream Outage Safety** | Scraper failure flags scrape run without mutating published offers | Scrape run marked `FAILED` (classification `TIMEOUT`); live offers untouched | **PASS** |

## 4. Network Boundary & Security Controls

1. **Loopback Mutation Guard (`adminNetworkGuard`)**:
   - All HTTP state mutations (`POST`, `PUT`, `DELETE`, `PATCH`) on the admin port are restricted to `127.0.0.1` / `::1` or authorized loopback tunnels.
   - Remote requests are rejected with HTTP 403 `FORBIDDEN_NETWORK_BOUNDARY`.
   - `X-Forwarded-For` spoofing is rejected: headers are ignored unless direct socket IP matches `TRUSTED_PROXIES`.
2. **Direct Publication Block**:
   - `PATCH /api/offers/:id` strictly prohibits direct transition to `PUBLISHED` (`db_status = 'PUBLISHED'` returns HTTP 400).
   - Publication can only occur via operator-driven `POST /api/sync/:id` or `POST /api/offers/:id/transition` with action `PUBLISH`.
3. **Public API Least Privilege**:
   - Consumer public API runs with restricted DB role: read-only access to published views, no access to staging tables, credentials, or audit logs.
